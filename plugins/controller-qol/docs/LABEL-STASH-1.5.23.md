Resolve by export name, never that RVA. Private controller bridge guards are unchanged.

Shared deposit failure at 0x23AD80 was traced via read-only ReadProcessMemory from the running 1.3.1 loader. Comparing the full SharedOwnerBytes body found differences only at offsets 95 and 96: the previous-season CALL at +0x5E now has displacement 2D 05 BF 03 instead of 5F 04 BF 03. The old captured wrapper target 0x3E2B242 was documented as runtime-generated, not stable. New thunk RVA 0x3E2B310 is FF25 with RIP-relative slot RVA 0x3E2A8A8, targeting D2RCore+0x1C9E00. Core SHA256: 2A868D013D2E0830BD2D9E04B918B19E46A73CF726C833E70D089B948FDEB5A2.

Disassembly of core+0x1C9E00 shows an output-vector argument in RCX, vector population, filtering of owner records, client-unit lookup using owner ID with type 0, and compaction. The caller's owner-vector bounds checks and BankPanel+0x168/+0x170 page selection remain byte-identical. 1.5.23 accepts the original complete owner guard OR identical body outside only the CALL rel32, an FF25 import thunk, destination exactly within loaded D2RCore at reviewed RVA 0x1C9E00, and 192 fixed target bytes. No arbitrary detours or changed opcodes/body are accepted. Fixed target bytes live in shared_owner_compatibility.h. The native owner resolver and native transfer still execute; we do not call the private core function directly. A future core change fails closed until re-reviewed.
